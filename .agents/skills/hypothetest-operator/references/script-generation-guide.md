# Script Generation Guide

Governs how the Operator generates sampling/execution scripts for during-phase
observation. The generated script is a bash or Python file that the Operator
produces as part of blueprint compilation, alongside compose assets.

## Output discipline

Stdout is for the LLM — one structured line per event. Every stdout line costs
tokens; the script must be concise.

Detailed data goes to files. Raw tool output goes to archive files.

```
stdout (LLM reads):     [tag] key=value key=value ...
TOON files (Analyst):   structured time-series summary
archive/ (debugging):   raw tool output
```

## Log format convention

One line per event. Tags: `[start]`, `[sample]`, `[phase_complete]`,
`[phase_failed]`, `[error]`, `[skip]`, `[summary]`.

```
[start] variation=baseline repeat=1 phase=load_data interval=10s
[sample] t=10 cpu_pct=45 heap_pct=62 gc_old=3 tp_write_queue=0
[sample] t=20 cpu_pct=78 heap_pct=71 gc_old=5 tp_write_queue=12
[phase_complete] variation=baseline repeat=1 phase=load_data elapsed=185s exit=0
[summary] variation=baseline repeat=1 phase=load_data samples=18 limiter=cpu
```

## File output separation

| Destination | Content | Consumer |
|---|---|---|
| stdout | Status lines (above format) | LLM / Operator |
| `evidence/during/<v>-<r>-<p>-samples.toon` | Structured time-series | Analyst |
| `evidence/during/<v>-<r>-<p>-raw/` | Raw tool output per sample | Debugging |

## TOON output shape

```toon
samples[N]{t,cpu_pct,heap_pct,gc_old_count,gc_old_ms,tp_write_queue,tp_write_rejected,tp_search_queue,disk_io_pct,mem_used_pct}:
  10,45,62,3,120,0,0,2,15,71
  20,78,71,5,340,12,0,4,42,73
```

Fields vary by active methods and packages. The script writes what it collects.

## Concurrency patterns

Background phase process + foreground sampling loop:

```bash
# Start phase in background
run_phase "$variation" "$phase" &
PHASE_PID=$!

# Sampling loop
while kill -0 "$PHASE_PID" 2>/dev/null; do
  collect_sample "$t"
  t=$((t + INTERVAL))
  sleep "$INTERVAL"
done

# Capture exit code
wait "$PHASE_PID"
PHASE_EXIT=$?
```

PID tracking with `trap` for signal handling. Cleanup on EXIT/INT/TERM.

## Sampling edge cases

| Case | Behavior |
|---|---|
| Tool takes longer than interval | Skip that sample, don't queue |
| Phase finishes mid-sample | Complete current sample, record phase exit |
| Tool not available | Log once with `[skip]`, don't spam |
| Phase exits non-zero | Collect final sample, record exit code, continue |
| Phase duration <15s | Log `[skip] reason=short_phase`, no sampling |

## Script skeleton

Every generated script follows this structure:

```
1. Validate prerequisites (tools available, endpoints reachable)
2. Phase execution loop: for variation × repeat
3. Background phase + sampling loop
4. Write summary TOON per variation×repeat×phase
5. Write overall evaluation summary
6. Exit with appropriate code
```

## Idempotency

The script can be re-run on a failed variation without corrupting previous
results. Output files are namespaced by `<variation>-<repeat>-<phase>`.

## Error handling

Distinguish between:

- **Phase failures** — record, continue to next variation×repeat
- **Infrastructure failures** — abort with clear message (endpoint unreachable,
  disk full, permission denied)

Never swallow errors silently. Every non-zero exit or failed collection attempt
produces a log line.

## Package collection commands

Reference commands per package (the script adapts based on what's prescribed):

| Package | Collection pattern |
|---|---|
| `elasticsearch_api` | `curl -s $ES_URL/_nodes/stats` → jq extract |
| `sysstat` | `iostat -x 1 1`, `mpstat 1 1` → awk extract |
| `procps` | `vmstat 1 2` (second line), `free -b` |
| `jdk_tools` | `jstat -gcutil $PID 1 1` |
| `perf` | `perf stat -p $PID sleep 1` |
| `bpftrace` | run `.bt` script or one-liner, capture output |
| `darwin_tools` | `vm_stat`, `iostat` |
